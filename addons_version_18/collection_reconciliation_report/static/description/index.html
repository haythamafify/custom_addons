Collection Reconciliation Report

Enterprise-grade payment-to-invoice allocation analytics built on raw SQL — no Odoo ORM overhead, maximal performance.

Why This Module Exists

Odoo's native accounting shows you the balance of an invoice. It does not tell you exactly which payment settled which portion of which invoice when one payment covers multiple invoices or a single invoice is paid in instalments. This module fills that gap with a SQL-backed analytical view and a real-time KPI dashboard.

Key Capabilities

  • Per-allocation analytics — every account_partial_reconcile row is normalised into a human-readable line: payment date, invoice, collected amount, residual, delay days.
  • KPI dashboard — collection efficiency %, recovery ratio %, overdue exposure, monthly growth, average delay, top collectors.
  • Materialised-view toggle — flip the switch in Settings to use a PostgreSQL materialised view for sub-second queries on 10M+ rows.
  • XLSX export — grouped, subtotalled, branded Excel with company logo, freeze panes, and professional formatting.
  • Smart buttons — one-click navigation from a partner form to all their reconciliation records.

What You Get

Detailed Reconciliation Lines

Every payment-invoice pair rendered as a row. Filter, group, pivot, graph — whatever your team needs.

Collection efficiency, recovery ratio, overdue exposure, monthly growth, top 3 collectors — SQL-calculated, parameterised, injection-safe.

Technical Highlights — Not Found in Any Competitor Module

  • pg_try_advisory_lock — prevents duplicate concurrent materialised-view refreshes. No other Odoo module uses PostgreSQL advisory locks for refresh safety.
  • Multi-stage CTE architecture — 6 chained WITH clauses (product_data → reconcile_base → normalized → final_allocations → product_data join) for maintainable, optimisable SQL.
  • Materialised-view toggle — enabled per-database via ir.config_parameter. Standard view for small DBs, materialised for production-scale.
  • Parameterised KPI SQL — stale_hours is a bind parameter, never interpolated. Injection-safe even if the setting store is compromised.
  • Dynamic XLSX registration — the XLSX report class only registers when OCA report_xlsx is installed. No broken dependencies.

Supported Scenarios

✅ Fully Paid On Time

Invoice created, paid before due date. payment_state = 'paid', delay = 0.

✅ Fully Paid Late

Payment arrives after due date. Delay days > 0 — visible in the report and KPI average.

✅ Partially Paid

Customer pays less than invoice total. Residual > 0, payment_state = 'partial'.

✅ Overdue / Unpaid

Invoice past due with no payment. Contributes to Overdue Exposure KPI.

✅ Multi-Payment Allocation

One invoice settled by two separate payments. Both allocations appear, allocation_count = 2.

✅ Credit Note Offset

out_refund reconciled against an invoice. Properly normalised with correct polarity.

Dependencies
